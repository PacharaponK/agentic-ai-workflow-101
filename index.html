00BIG PICTURE

AI Agent คืออะไร และทำไมต้องเรียน?

“Agent” คือระบบ AI ที่ไม่ได้แค่ ตอบคำถามทีละครั้ง แต่สามารถ วางแผน ลงมือทำ และตรวจสอบผลลัพธ์ด้วยตัวเอง เป็นวงรอบ จนกว่างานจะเสร็จ โดยใช้ “เครื่องมือ” (tools) เพื่อโต้ตอบกับโลกจริง เช่น อ่าน/เขียนไฟล์ รันคำสั่ง หรือค้นเว็บ

💬
Chatbot ธรรมดา

รับข้อความ → ตอบกลับ จบในรอบเดียว ไม่ลงมือทำอะไรเอง

🔧
LLM + Tools

เรียกใช้เครื่องมือได้ แต่ยังควบคุมโดยลำดับขั้นที่ตายตัว

🤖
AI Agent

ตัดสินใจเองว่าจะใช้เครื่องมืออะไร เมื่อไหร่ และวนซ้ำจนเสร็จ

🧭
แผนที่ของเอกสารนี้

เราจะไล่จาก แนวคิด (Workflow) → สภาพแวดล้อม (Harness) → ไฟล์ควบคุมพฤติกรรม (AGENT.md, SKILL.md, DESIGN.md) → การลงมือทำจริง

01CORE CONCEPT

Agentic AI Workflow

หัวใจของ agent คือ วงลูป (agent loop) ที่ทำซ้ำไปเรื่อย ๆ จนกว่าจะบรรลุเป้าหมาย ต่างจาก workflow แบบเดิมที่กำหนดทุกขั้นตอนไว้ล่วงหน้า

วงจรการทำงาน 4 ขั้น

① Perceive
รับเป้าหมาย + บริบท
→
② Plan
คิดว่าจะทำอะไรต่อ
→
③ Act
เรียกใช้ tool
→
④ Observe
ดูผล แล้วประเมิน
↺ วนกลับไปขั้น ② จนกว่างานจะเสร็จ (Reasoning + Acting = ReAct loop)

Workflow แบบกำหนดเอง vs แบบ Agentic

มุมมองPredefined WorkflowAgentic Workflow
ลำดับขั้นตอนกำหนดตายตัวล่วงหน้าโมเดลตัดสินใจเองแบบ dynamic
ความยืดหยุ่นต่ำ — เจอเคสใหม่ต้องแก้โค้ดสูง — ปรับตัวตามสถานการณ์
ความคาดเดาได้สูงปานกลาง (ต้องมี guardrail)
เหมาะกับงานซ้ำ ๆ ที่รู้ขั้นตอนชัดงานเปิดกว้าง ปลายทางไม่แน่นอน

รูปแบบ (Patterns) ที่พบบ่อย

  • ReAct — สลับ “คิด (reason)” กับ “ลงมือ (act)” ทีละก้าว
  • Planning — วางแผนทั้งหมดก่อน แล้วค่อยลงมือทีละขั้น
  • Reflection — agent ตรวจงานตัวเองแล้วแก้ไขซ้ำ
  • Multi-agent — แบ่งงานให้ agent ย่อยหลายตัวทำคู่ขนาน (เช่น orchestrator + sub-agents)
💡
กุญแจสำคัญ

Agent ที่ดีไม่ได้วัดที่ “ฉลาดแค่ไหน” แต่วัดที่ ลูปหยุดถูกจังหวะ — รู้ว่าเมื่อไหร่งานเสร็จ เมื่อไหร่ควรถามมนุษย์ และเมื่อไหร่ต้องยอมแพ้

02RUNTIME

Agent Harness

ตัวโมเดล (LLM) เพียงอย่างเดียว ทำอะไรไม่ได้ มันแค่พ่นข้อความออกมา — Harness คือโปรแกรมที่ห่อหุ้มโมเดลไว้ คอยรันลูป จัดการ context และเชื่อมต่อกับเครื่องมือจริง

Harness ทำหน้าที่อะไรบ้าง

🔁
รัน Agent Loop

ส่ง prompt → รับคำตอบ → ถ้าโมเดลขอใช้ tool ก็ไปเรียกให้ → ส่งผลกลับ → วนซ้ำ

🛠️
จัดการ Tools

นิยามว่ามี tool อะไรบ้าง (อ่านไฟล์, รัน shell, ค้นเว็บ) และบังคับใช้สิทธิ์ (permission)

🧠
บริหาร Context

ใส่ system prompt, ประวัติสนทนา, ไฟล์ที่เกี่ยว และ “บีบอัด” เมื่อ context ยาวเกิน

🛡️
Guardrails

ขออนุญาตก่อนทำสิ่งที่อันตราย, จำกัดจำนวนรอบ, กรอง output

กายวิภาคของหนึ่งรอบ (one turn)

agent_loop.py — pseudo-code
while not task_done:
    response = model.generate(
        system   = system_prompt,   # รวมเนื้อหาจาก AGENT.md
        messages = conversation,
        tools    = available_tools,
    )

    if response.wants_tool():
        result = harness.run_tool(response.tool_call)  # ← Harness ลงมือจริง
        conversation.append(result)
    else:
        task_done = True   # โมเดลบอกว่าเสร็จแล้ว
🔍
ตัวอย่าง Harness ในชีวิตจริง

Claude Code, Cursor, OpenAI Codex CLI, LangGraph — ทั้งหมดนี้คือ harness ที่ต่างกันที่ดีไซน์ของลูป, ชุด tools, และวิธีจัดการ context แต่หลักการเดียวกัน

03CONFIGURATION

AGENT.md / CLAUDE.md

04CAPABILITY

SKILL.md

ถ้า AGENT.md คือ “ความรู้ที่ต้องรู้เสมอ” — Skill คือ “ความเชี่ยวชาญเฉพาะทางที่หยิบมาใช้เมื่อจำเป็น” มันคือชุดคำสั่ง + สคริปต์ + ทรัพยากร ที่ห่อรวมเป็นแพ็กเกจ และ โหลดเข้า context เฉพาะตอนที่เกี่ยวข้อง

หลักการ Progressive Disclosure

Agent ไม่ได้อ่านทุก skill ตลอดเวลา — มันเห็นแค่ ชื่อ + คำอธิบาย ก่อน เมื่อ task ตรงกับ description ถึงจะโหลดเนื้อหาเต็มเข้ามา ช่วยประหยัด context มหาศาล

เห็นแค่ metadata
name + description
→
task ตรงกับ skill
โมเดลตัดสินใจเรียก
→
โหลด SKILL.md เต็ม
+ สคริปต์/ไฟล์แนบ

โครงสร้างโฟลเดอร์ skill

## แยกหน้า
ดูรายละเอียด API ใน `references/api-guide.md`

05FOUNDATION

Design System คืออะไร?

Design System คือ "ภาษากลาง" ของทีมพัฒนา — ชุดของ หลักการ, รูปแบบ, และองค์ประกอบที่ใช้ซ้ำได้ ซึ่งทุกคน (รวมถึง agent) ยึดเป็นมาตรฐานเดียวกัน เพื่อให้ผลลัพธ์ออกมาสอดคล้องกันทั้งระบบ

🧩
Design System กับ DESIGN.md สัมพันธ์กันอย่างไร?

Design System = แนวคิดและหลักการออกแบบของทีม (อาจอยู่ใน Figma, Storybook ฯลฯ)
DESIGN.md = ไฟล์ที่ แปลง Design System ให้อยู่ในรูปที่ agent อ่านได้ — design tokens เป็น YAML + rationale เป็น markdown
กล่าวได้ว่า DESIGN.md คือ "สำเนาของ Design System สำหรับ AI"

3 ระดับขององค์ประกอบ Design System

🎨
Foundations

สิ่งพื้นฐานสุด: สี, ตัวอักษร, spacing, ระบบ grid — กฎที่ทุกอย่างต้องอิง

🧱
Components

ชิ้นส่วนที่ประกอบซ้ำได้: Button, Card, Modal, Form — แต่ละตัวมี spec ชัดเจน

📐
Patterns

วิธีประกอบ components เข้าด้วยกัน: form validation pattern, navigation pattern

Design System ในโลก Agentic AI

เมื่อ agent ถูกขอให้ "สร้าง UI" หรือ "เพิ่มฟีเจอร์" โดยไม่มี Design System — มันต้องตัดสินใจเรื่องสีเอง, ขนาดเอง, รูปแบบเอง ซึ่งผลลัพธ์มักไม่สอดคล้องกับส่วนอื่นของระบบ Design System จึงเป็น constraint ที่ดี ที่ลดการตัดสินใจของ agent และรับประกัน consistency

สิ่งที่ควรนิยามใน Design System สำหรับ Agent

หมวดตัวอย่างที่ควรระบุ
Visual Tokenชื่อสี (เช่น --color-primary), ขนาด font, spacing scale
Component Contractprops ที่รับได้, state ต่าง ๆ (default/hover/disabled), variant
Naming Conventionรูปแบบชื่อไฟล์, คลาส, ตัวแปร ที่ใช้ทั้งโปรเจกต์
Do / Don'tตัวอย่างสิ่งที่ทำได้และห้ามทำ (พร้อมเหตุผล)

ตัวอย่างการอ้างอิง Design System ใน AGENT.md

CLAUDE.md — ส่วนที่อ้างถึง Design System
## Design System
- ใช้ Tailwind CSS — ดู token ที่ `tailwind.config.ts`
- สีหลัก: `brand-600`, สีรอง: `neutral-500`
- Component library: shadcn/ui — ดูของที่มีอยู่ใน `src/components/ui/`
  ก่อน สร้างใหม่ก็ต่อเมื่อไม่มี component ที่ตรงความต้องการ
- Spacing: ใช้ scale จาก Tailwind เท่านั้น (ห้ามใช้ px ตรง ๆ)
💡
Design System ที่รู้จักกันดี

Material Design (Google) · Ant Design · shadcn/ui · Radix UI — ถ้าโปรเจกต์ใช้ระบบเหล่านี้อยู่แล้ว ให้ระบุใน AGENT.md ว่าใช้อะไร agent จะปฏิบัติตามแนวทางของระบบนั้นได้ทันที

06VISUAL CONTRACT

DESIGN.md

DESIGN.md คือเอกสาร design system ที่ agent อ่านเพื่อสร้าง UI ให้สอดคล้องกันทั้งโปรเจกต์ — ไม่ใช่แผนฟีเจอร์ แต่คือ "ภาษาสายตา" ที่แปลง Design System ให้เป็นรูปแบบที่ AI เข้าใจได้ ทุกหน้าจอที่ agent สร้างจะยึดสี ตัวอักษร และ pattern ชุดเดียวกัน

💡
DESIGN.md เป็น "living artifact"

ไม่ใช่ไฟล์ config ที่ตายตัว — มันเติบโตไปพร้อมกับ design ของคุณ agent สร้างมันให้ คุณปรับแต่ง แล้วมันก็ถูกนำไปใช้กับหน้าจอต่อ ๆ ไปโดยอัตโนมัติ

โครงสร้าง 2 ชั้น

ทุก DESIGN.md มีสองชั้นที่ทำงานร่วมกัน:

⚙️
YAML Front Matter

Design tokens ที่ machine-readable — ค่าสีเป็น hex, คุณสมบัติ font, spacing scale แน่นอน agent ใช้ค่าเหล่านี้เป็นตัวเลขจริง

📝
Markdown Body

Design rationale ที่ human-readable — อธิบาย ว่าทำไม ค่าเหล่านั้นถึงถูกเลือก ช่วยให้ agent เข้าใจเจตนาและตัดสินใจส่วนที่ token ครอบคลุมไม่ถึง

ตัวอย่าง DESIGN.md (dark-themed productivity app)

DESIGN.md
---
name: DevFocus Dark
colors:
  primary:    "#2665fd"   # สีหลัก — ปุ่ม, link, accent
  secondary:  "#475569"   # สีรอง
  surface:    "#0b1326"   # พื้นหลัง card / panel
  on-surface: "#dae2fd"   # ข้อความบน surface
  error:      "#ffb4ab"
typography:
  body-md:
    family: "Inter"
    size:   "16px"
    weight: 400
  heading-lg:
    family: "Inter"
    size:   "32px"
    weight: 700
spacing:
  base: "4px"   # หน่วยพื้นฐาน × 1, 2, 4, 8 ...
---

# DevFocus Dark — Design Rationale

## ปรัชญาภาพรวม
ธีมมืดเข้มออกแบบมาเพื่อลด eye strain ระหว่างทำงานนาน ๆ
สีน้ำเงินเป็น primary เพื่อให้ดูน่าเชื่อถือและโฟกัสได้

## สี
หลีกเลี่ยงสีขาวบริสุทธิ์ (#fff) บน surface มืด — ใช้ on-surface
แทนเพื่อลด contrast ratio ที่แรงเกินไป

## Typography
ใช้ Inter เพราะอ่านง่ายบนจอความละเอียดสูง
ขนาด heading ต้องแตกต่างกันอย่างน้อย 1.5× เพื่อให้ hierarchy ชัด

3 วิธีสร้าง DESIGN.md

🤖
ให้ Agent สร้าง

บอก "vibe" ที่ต้องการ เช่น "มืด เรียบ มินิมัล" — agent แปลงความตั้งใจนั้นเป็น token และ guideline ให้ทันที

🎨
นำมาจาก Branding

ให้ URL หรือรูปภาพ brand ที่มีอยู่ — agent ดึง palette, typography, และ style pattern ออกมาสร้าง DESIGN.md อัตโนมัติ

✍️
เขียนเอง

ผู้ใช้ขั้นสูงเขียน DESIGN.md โดยตรง — ใช้แค่ markdown + YAML มาตรฐาน ไม่มี syntax พิเศษ

08BEST PRACTICES

หลักปฏิบัติที่ทำให้ Agent ทำงานดี

✍️ การเขียนคำสั่ง

  • สั้น กระชับ ชัดเจน — เขียนเฉพาะที่ไม่ชัดจากโค้ด
  • ใส่ “ข้อห้าม” ให้ชัด ดีกว่าบอกแต่สิ่งที่ทำได้
  • ให้ตัวอย่างจริงดีกว่าอธิบายลอย ๆ

🧩 การจัดการ Context

  • แยกความรู้เป็น skill อย่าอัดทุกอย่างใน AGENT.md
  • ใช้ description ที่มี trigger words ชัดเจน
  • แตกงานใหญ่เป็น task ย่อยใน DESIGN.md

🛡️ ความปลอดภัย

  • ตั้ง permission ให้ขออนุญาตก่อนทำสิ่งอันตราย
  • ไม่เก็บ secret / key ไว้ในไฟล์ที่ agent อ่าน
  • ให้มนุษย์ review แผน (DESIGN) ก่อนลงมือ

🔁 การทำงานเป็นรอบ

  • ให้ agent รัน test เพื่อ “ตรวจงานตัวเอง”
  • ทำทีละ task เล็ก ๆ แล้ว commit บ่อย ๆ
  • กำหนดเงื่อนไขหยุดลูปให้ชัด
🌟
กฎทอง

ปฏิบัติกับ agent เหมือน นักพัฒนาใหม่ที่เก่งแต่ยังไม่รู้จักโปรเจกต์ — สิ่งที่คุณจะบอกเขาในวันแรก คือสิ่งที่ควรอยู่ใน AGENT.md / SKILL.md / DESIGN.md
